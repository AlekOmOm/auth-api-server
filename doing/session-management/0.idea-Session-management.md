# Session Management Infrastructure

## Problem

Auth-System users experience fragmented and inconsistent authentication states when navigating across different contexts within the ecosystem. This creates several critical pain points:

-   **Context-Switching Memory Loss:** Users lose their authentication state and tenant context when moving between client applications, the auth-system management interface, and API-driven workflows, forcing repeated logins and context re-establishment.
-   **Multi-Tenant Schema Confusion:** Without persistent session-based tenant detection, users may inadvertently operate on the wrong database schema, leading to data isolation breaches or "user not found" errors when their session doesn't carry forward the correct tenant context.
-   **Hybrid Authentication Complexity:** The system supports both session-based authentication (for human users) and JWT-based authentication (for API clients), but lacks a unified session management layer that can seamlessly bridge these two paradigms while maintaining security boundaries.
-   **Session State Bloat & Performance:** Ad-hoc session data accumulation leads to oversized session objects that slow down request processing, increase memory footprint, and create inconsistent session validation logic across different middleware layers.
-   **Cross-Flow User Experience Breaks:** A user authenticated in a client application who needs to manage their client-server configuration experiences jarring authentication handoffs, losing context about which tenant they were operating within.
-   **Stateless vs Stateful Authentication Gaps:** The coexistence of stateful sessions (Express) and stateless tokens (JWT) creates gaps where session state doesn't properly propagate to JWT claims or vice versa, leading to authorization inconsistencies.

## Solution

Implement a **Centralized Session Management Infrastructure** that provides a clean, minimal, and consistent session state abstraction across all authentication flows and user contexts within the Auth-System:

1.  **Minimal Session Schema Enforcement:**
    *   Establish a canonical 7-key session structure via `setObj`: `userId`, `role`, `schema`, `ownerId`, `sessionId`, `isAuthenticated`, `allowedUrls`.
    *   Prevent session bloat by rejecting any data that doesn't fit this schema, ensuring consistent memory usage and fast serialization.
    *   Provide strongly-typed session utilities that enforce this structure across all middleware and service layers.

2.  **Intelligent Schema Detection & Persistence:**
    *   Automatically detect and persist tenant schema context from multiple sources: `Referer` headers, explicit `identifierUrl` parameters, and JWT token claims.
    *   Cache detected schema information in the session to avoid repeated database lookups while maintaining data freshness.
    *   Implement fallback hierarchies (explicit parameter → Referer → JWT → default) with clear precedence rules.

3.  **Unified Authentication Bridge:**
    *   Seamlessly convert between session-based and JWT-based authentication contexts without losing user state or tenant information.
    *   Automatically populate JWT claims from session data when issuing API tokens, ensuring consistent authorization context.
    *   Enable session restoration from valid JWT tokens when users transition from API contexts back to web interfaces.

4.  **Role-Based Session Enhancement:**
    *   Dynamically enhance sessions with role-specific data: client-server ownership for 'owner' role, system access for 'admin' role, tenant boundaries for 'user' role.
    *   Implement lazy-loading patterns for expensive role data that doesn't need to persist in the core session object.
    *   Provide role transition capabilities (e.g., admin impersonating a tenant user) with proper audit trails.

5.  **Cross-Context State Preservation:**
    *   Maintain authentication continuity when users navigate between client applications and auth-system management interfaces.
    *   Preserve tenant context across authentication handoffs, ensuring users don't lose their operational context.
    *   Implement secure session sharing mechanisms for same-origin and cross-origin scenarios within the auth ecosystem.

## Rabbit Holes

-   **Over-Engineering Session Persistence:** Implementing complex session replication, clustering, or distributed caching before understanding actual scale requirements, instead of starting with simple in-memory sessions and scaling incrementally.
-   **Session Data Expansion Creep:** Allowing gradual addition of "just this one field" to sessions, eventually recreating the bloat problem that the minimal schema was designed to prevent.
-   **Complex Cross-Domain Session Sharing:** Attempting to implement sophisticated cross-domain session sharing mechanisms (iframe messaging, postMessage protocols) before validating that simple same-origin solutions meet most use cases.
-   **Premature Session Analytics:** Building extensive session analytics, user journey tracking, or behavioral analysis into the core session management layer instead of keeping it focused on authentication state management.
-   **JWT-Session Perfect Synchronization:** Trying to maintain perfect real-time synchronization between JWT tokens and session state, instead of accepting eventual consistency and designing for graceful degradation.
-   **Role Hierarchy Over-Complexity:** Designing elaborate role inheritance, delegation, or permission matrix systems when simple flat roles ('user', 'owner', 'admin') cover most actual use cases.

# Analysis of Session Management Infrastructure

## Exploring the Problem Space

The session management challenge goes deeper than typical web authentication because of the Auth-System's unique multi-tenant, multi-flow architecture:

1.  **Invisible Infrastructure Expectations:** Users expect seamless authentication without understanding the complexity underneath. What specific user journeys create the most friction when session state is lost? (e.g., owner managing multiple client-servers, users moving between client apps with shared authentication).

2.  **Schema Detection Failure Modes:** When automatic schema detection fails (blocked Referer, ambiguous URLs, misconfigured client_servers), what is the user experience? Do they see cryptic errors, get redirected to defaults, or face complete authentication failure?

3.  **Performance vs Consistency Trade-offs:** The 7-key minimal session approach optimizes for performance, but how often do developers need derived data (client_mode, app_name, full user profile) that requires additional database hits? Is the performance gain worth the development complexity?

4.  **Security Boundaries in Hybrid Auth:** JWT tokens can contain more context than sessions, but sessions can be immediately revoked while JWTs cannot. How do security incidents (compromised owner accounts, suspicious API usage) get handled across both authentication methods?

5.  **Multi-Device Session Coordination:** A single user might have sessions across multiple devices/browsers and API tokens for different client applications. How should session limits, concurrent access, and device management be handled?

6.  **Tenant Context Leakage Risks:** With automatic schema detection, what prevents malicious actors from manipulating Referer headers or identifierUrl parameters to gain access to other tenants' schemas?

## Steelmanning the Solution & Potential Improvements

The proposed minimal session architecture is solid, but can be enhanced for robustness and developer experience:

1.  **Session Validation & Health Checks:**
    *   Implement session integrity validation that checks for corrupted or inconsistent session state (e.g., userId exists but schema is null).
    *   Provide session debugging endpoints (dev/staging only) that reveal the complete session state and detection history for troubleshooting.
    *   Add session health metrics: average session size, detection success rates, role distribution.

2.  **Enhanced Schema Detection Pipeline:**
    *   Implement schema detection caching with TTL to reduce database hits for frequently accessed client_servers.
    *   Add schema "confidence scores" based on detection method (explicit parameter = 100%, Referer = 80%, default = 20%) for better debugging.
    *   Support schema override mechanisms for admin users who need to operate across multiple tenants.

3.  **Developer Experience Improvements:**
    *   Provide typed session utilities: `getRequiredUserId(session)`, `getOptionalSchema(session)` that throw descriptive errors for missing required fields.
    *   Implement session state logging in development mode that traces all setObj calls and their sources.
    *   Create session testing utilities that can mock different authentication contexts for unit tests.

4.  **Graceful Degradation Patterns:**
    *   Define clear fallback behaviors when session data is incomplete: anonymous browsing modes, guest access patterns, limited functionality states.
    *   Implement session recovery mechanisms that can rebuild session state from database queries when critical data is missing.
    *   Provide user-friendly error messages that explain authentication requirements without exposing internal session structure.

5.  **Advanced Role & Context Management:**
    *   Support temporary role elevation (e.g., user becoming admin for support cases) with automatic expiration.
    *   Implement "session context switching" for admins who need to view the system from different user perspectives.
    *   Add audit logging for all session modifications, especially role changes and schema assignments.

6.  **Session Lifecycle Optimization:**
    *   Implement lazy session initialization that only creates database sessions when authentication is required.
    *   Provide session pre-warming for known user workflows (e.g., owner accessing client-server management).
    *   Add session cleanup automation that removes orphaned sessions and expired authentication state.

## Open Questions Worth Exploring

1.  **Session Storage Strategy:** Should the system migrate from in-memory sessions to Redis/database storage as it scales, and what are the performance implications of each approach for the 7-key minimal schema?

2.  **Cross-Application Session Sharing:** How should sessions be shared between the main auth-system interface and client applications? Same-origin cookies, secure token passing, or completely separate authentication contexts?

3.  **Session Security Boundaries:** What data should never be stored in sessions vs. what should never be stored in JWT tokens? How do we prevent sensitive information from leaking across these boundaries?

4.  **Role Transition Workflows:** When a user transitions from 'user' to 'owner' (by registering their first client-server), how should the session be updated? Immediate refresh, re-authentication requirement, or seamless upgrade?

5.  **Schema Detection Validation:** Should the system validate that a detected schema actually matches the authenticated user's access rights, or rely on downstream authorization checks?

6.  **Session Monitoring & Alerting:** What session-level metrics indicate system health vs. security issues? (e.g., high schema detection failure rates, frequent role transitions, unusual session patterns)

7.  **Backward Compatibility:** As the session schema evolves, how will the system handle sessions created with older versions of the setObj structure?

8.  **Multi-Tenant Session Isolation:** How can the system guarantee that session data from one tenant never leaks into another tenant's context, even in memory or caching layers?

9.  **API Rate Limiting:** Should rate limiting be applied per-session, per-user, or per-schema? How does this interact with both session-based and JWT-based authentication?

10. **Session Testing & Debugging:** What tools should be provided to developers and system administrators for diagnosing session-related issues in production without exposing sensitive user data?

## Implementation Alignment Checklist (derived from current code review)

1. **Enforce the 7-key whitelist in `setObj`**  
   Reject or strip any extraneous properties before merging to guarantee minimal session size and prevent silent bloat.
2. **Add runtime/compile-time validation utilities**  
   Provide a lightweight schema validator (e.g. `zod`) or migrate request/session utils to TypeScript for early error detection.
3. **Complete the Session ↔ JWT bridge**  
   • Issue JWTs directly from session data (`issueApiTokenFromSession`) so claims mirror `userId`, `role`, `schema`, `ownerId`, `allowedUrls`.  
   • Ensure middleware can also recreate an Express session from a valid JWT when users move back to the web UI.
4. **Extend `Session.toExpressSession()` parity**  
   Include `ownerId`, `isAuthenticated`, and `allowedUrls` to keep the in-memory session consistent with the database model.
5. **Wire `POOL_CONTEXTS` to connection logic**  
   After schema detection, set the appropriate pool context to guarantee queries hit the correct connection pool.
6. **Introduce integrity & completeness guard**  
   Middleware `requireCompleteSession` should fail fast if `userId` or `schema` is missing or the session is expired.
7. **Lazy role-specific enrichment**  
   Provide `withRoleData(session)` that attaches owner/admin extras on demand rather than persisting them in the core object.
8. **Metrics & scheduled cleanup**  
   • Expose session health metrics (size, expiry, detection failures).  
   • Schedule `service.session.deleteExpired` via a cron/worker.
9. **Cookie / SameSite strategy for multi-subdomain flows**  
   Ensure cookies share the same `domain` and `SameSite=None; Secure` settings where cross-origin auth is required.
10. **Document testing helpers**  
    Ship factory methods and mocks that allow unit/e2e tests to spin up valid sessions quickly without DB round-trips.
